# 两个真实事故的复盘

取证时间 2026-11-15。两个事故都发生在同一台开发机上,来自**两个不同的 agent 宿主产品**。

## 方法说明

结论全部来自**读取磁盘上的会话日志**,不是来自会话上下文,也不是来自当事人回忆。

- 事故 A:一条约 45 MB 的 CLI 会话日志(每行一次完整模型请求 + 响应)。
- 事故 B:一份压缩会话日志(压缩后约 5 MB,解压约 12 MB)。

两条取证纪律,写在这里是因为它们影响结论的可信度:

1. **跨进程:** agent 没有、也不该有对其他会话的隐式访问权。能下结论,是因为日志被写到了磁盘上。
2. **多帧压缩的陷阱:** 一份会话日志是**逐次追加的多帧压缩文件**。用单次解压调用只会解出第一帧,本文件只会得到几百字节 —— 一个**完美的假阴性**:解压"成功"、内容为空、于是"没查到问题"。
   必须按帧头 magic 切帧逐段解。任何"我扫过日志了,没有这个问题"的结论,都要先回答:你解了几帧?

> 这一条直接导致过一次错误结论:早前一轮只扫了一个产品的会话,得出"本机查不到浏览器撞车"。补扫另一个产品的会话日志后,现场是确凿的。**扫描覆盖面本身就是结论的边界。**

## 事故 A:共享 CDP 端点被关闭

### 资源形态

一个**已登录的 headed 浏览器实例**,通过固定端口暴露 CDP:

```
端点     http://127.0.0.1:<cdp-port>   (已登录,profile 里是登录态)
账号     <user> / 团队 <team>
站点     两个后台页面,共用同一个浏览器实例
所有权   全队同时只能一个 agent 驱动
```

连接方式:`connect_over_cdp("http://127.0.0.1:<cdp-port>")`。

这是教科书式的 **A 类 独占单例**:登录态存在 profile 里,无法并行复制;端口写死在所有脚本里;没有任何机制记录"谁现在持有它"。

### 现场记录(脱敏后逐字引用)

专职 agent 的报告:

> 「任务收尾时浏览器调试实例被关闭(`<cdp-port>` ECONNREFUSED,重试 2 次无效),最后几项改用公开文档站补齐。」

> 「调试实例被关闭了!浏览器挂了。需要检查 CDP 浏览器是否还活着 —— 剩下的流程都依赖它!如果被关,需要重启并带上调试端口参数。这是紧急事项。」

原始异常:

```
Error: BrowserType.connect_over_cdp: connect ECONNREFUSED 127.0.0.1:<cdp-port>
Call log:
  - <ws preparing> retrieving websocket url from http://127.0.0.1:<cdp-port>
```

同一条 `ECONNREFUSED` 在该会话中出现在多个互不重叠的时间窗口。

### 机制归类

| 特征 | 本案 |
|---|---|
| 固定端口 | 写死在所有脚本里 |
| 单例资源 | 一个已登录实例,无法并行复制 |
| 无租约 | 没有"谁现在持有它"的权威状态,靠聊天约定 |
| 无所有权证明 | 任何 agent 都能连,也都能关掉它 |
| 失败形态 | 硬失败,且**故障点离根因很远**:报错在连接处,根因是"共享实例被关掉了" |

### 后果链

1. 唯一入口的工作流中断。
2. agent **自动重试 2 次** —— 正是协议明令禁止的反模式:把控制冲突转化成时间浪费,两次重试没有带来任何新信息。
3. 最后几项任务改走公开文档,**信息完整度下降**。
4. 被当时的 agent 标记为"紧急事项",需要人工介入重启。

> **未证实:是谁关掉了它。** 是另一个 agent、是用户手工操作、还是浏览器自身退出,日志证明不了。
> 这份复盘只主张**机制**(共享单例、无所有权保护),不推断**凶手**。两者必须分开,否则复盘就变成了归责。

## 事故 B:编排层按数量计的硬闸门

### 资源形态

不是物理资源,是**编排配额**:一个"同时最多几个成员"的硬上限。

关键点:它与"最大并发子任务数"是**两个不同的限制**,但失败语义相同。

### 现场记录

第一次,编排者想再派一个专职 agent,被拒:

```
"type":"tool/result","content":[{"type":"text","text":"Error: team member limit reached"}],
"isError":true
```

编排者的当场推理(以下是据原会话推理整理的转述,**并非逐字**:原始记录是英文,中文是对照译文):

> Team member limit 8 reached. Currently: lead + <role-a>, … Limit is 8 members. So I'm already over?
>
> (译文)成员数上限到了。当前是:lead + <role-a>,……上限是 8 个成员。所以我已经超了?

也就是说:**连编排者自己都不确定当前有几个成员在跑。** 它只能从错误码反推。

原会话里这段推理是英文,数字(具体上限与在跑成员数)已隐去;上面给英文原话与中文对照,标注了"译文",不声称是同一语言的"原话"。**内部角色名已替换为 `<role-a>` 这类占位符**,句式与省略号保持原样。事故 A 那两段现场记录仍是脱敏后的原话(删去实例端口与平台标识),原始异常栈逐字保留。

第二次,四个派发调用挤在 **43 毫秒内全部被拒**(原始时间戳已转为相对偏移,四个偏移量保留):

```
+0 ms    Team member limit reached
+12 ms   Team member limit reached
+33 ms   Team member limit reached
+43 ms   Team member limit reached
```

整场会话里,这一类配额错误出现了 **9 次**,而几乎所有工具错误都是撞上限 —— 不是业务失败。

### 机制归类

**按"数量"计的硬闸门,不排队。**

- 满了**直接拒绝**,不是排队。
- 被拒的工作单元**根本没被创建出来**,静默消失。编排者只能从错误里知道自己少了一个 agent,不知道少了哪个、也没法补。
- 撞墙时编排者正在做的事是"想加人手" —— **资源最紧张的时刻恰恰是最想并行的时刻**,所以这个上限总是在最坏的时候咬人。

### 值得注意:当时的应对是去改配置

> 当时的推理:用户已经口头授权了提高上限的权力,所以"我有权限,但没有机制"。……让我找找有没有这个设置项。

遇到上限 → 想提高上限。这是把**容量问题**当**配置问题**解。真正的解法是**排队 + 资源可见**。

把上限从 N 调到 N×10 只是把撞墙时间往后推,并且让撞墙时的爆炸半径更大。

## 一个能解释失效的发现:团队已经手写过一份"租约协议"

同一份会话的交接文档里写明了几条约定:所有权上,**全队同时只能一个 agent 驱动**;操作纪律上,要求成员在使用前先在群里声明、用完立即说"已释放"、每次操作先确认当前在哪个后台页面(两个后台页面共用同一个浏览器,极易串台)、脚本用完不要关闭浏览器(会杀掉共享实例),进程结束自动断开即可。文档还附了两次真实事故的提醒。

文档还标注浏览器是「**最稀缺、最容易撞车**」的资源。

### 这段文字证明了三件事

1. **问题被准确识别过。** 团队知道它是单例、知道会串台、知道要"声明 / 释放"。
2. **他们造的正是手工版租约。** "在群里声明我要用浏览器" = 申请租约;"已释放" = 释放租约。这和 `acquire` / `release` 是**同一个抽象**,只不过载体是聊天消息。
3. **四条缺口各自对应一类可预见的失效;事故 A 能证实的只有第 4 条。**

| 手工租约的缺口 | 现场表现 |
|---|---|
| 聊天声明**不可强制** | 没有任何东西阻止第二个 agent 直接连端口 |
| 无人持有**所有权证明** | 所以谁都能关掉那个共享实例 |
| **没有 TTL** | 声明后崩溃或忘记,状态就永久脏掉 |
| **没有可查询的权威状态** | 只能靠人记住谁在用;编排者连成员数都要靠报错反推 |

事故 A 与手工协议的第 4 条缺口(无可查询的权威状态)吻合;其余三条属机制推断,没有现场证据。

这也是为什么"在提示词里写清楚"这条路的性价比是负的:写清楚只能减少**无知导致的**冲突,减少不了**激励导致的**冲突。想并行是正确激励,协议必须让并行变安全,而不是让人别并行。

## 缺口与对应机制

| 事故中的缺口 | 对应机制 |
|---|---|
| 谁在用那个端口,没有权威状态 | `acquire port:<cdp-port>` + `status` |
| 聊天声明不可强制 | 文件锁 `O_CREAT\|O_EXCL`,抢不到就是退出码 2 |
| 谁都能关掉共享实例 | 受保护工具守卫(能力,默认未启用:需在 `cordis.patch.yml` 里配 `protectedTools`,把关闭类工具绑定到租约,未持租约直接拒绝) |
| 声明后崩溃 → 状态永久脏 | TTL 过期可接管 + 接管日志 |
| 编排者不知道谁占着什么 | 实时占用注入到编排者上下文 |
| agent 失败后自己重试 | 协议铁律:抢不到就上报,禁止重试硬闯 |
| 上限满了工作单元静默消失 | **编排者侧排队重新调度**(允许:被拒的单元由 Lead 记录后下一轮再派、或换资源 —— 这是编排者的职责);**子 agent 侧 sleep 自等**(禁止:烧掉的是时间,编排者还会以为它在干活)。两者中文都叫"排队",本方案只允许前者 |

## 结论

- **事故 A 真实发生。** 证据:跨进程连接被拒的原始异常 + 专职 agent 的现场报告 + 工作流中断 + 重试 2 次无效。
- **事故 B 真实发生。** 证据:同一会话里配额错误出现 9 次,其中 4 次挤在 **43 毫秒**内(相对偏移 +0 / +12 / +33 / +43 ms)。
- 两者**是同一类问题的两个面**:一个撞的是"物理单例",一个撞的是"编排配额"。共同点是 —— **都没有资源面的可见性与仲裁**。
- 这两个事故**不能证明**这套方案有效。它们只证明问题真实存在。方案有效性目前只有功能测试,没有基准测试,见 [README](../README.md#边界与局限)。

## 证据强度(必须写在结论旁边)

| 项 | 状态 |
|---|---|
| 事故现场 | 2 个,**同一台机器**,来自 2 个不同产品 |
| 原始报错 | ✅ 事故 A 的异常栈为**逐字**,来自磁盘日志(仅脱敏端口/路径);事故 B 的 agent 报告是**脱敏后的转述**,不是逐字 |
| 根因(凶手) | ❌ 未证实,不做推断 |
| 跨机器复现 | ❌ 没有 |
| 修复前后基准测试 | ❌ 没有 |
| 上游采纳 | ❌ 无 |
