# 子 agent 资源仲裁层 —— 设计规格

版本 **v2** · 2026-11-17 · 前身 v1(2026-11-15) · 实现契约:[RESOURCE-MODEL-v2.md](RESOURCE-MODEL-v2.md) · 配套:[REPORT.md](../../_multiagent_resources/REPORT.md)

> **这份文档管「为什么这么设计」,契约管「必须怎么实现」。**
> 两者冲突时以 [RESOURCE-MODEL-v2.md](RESOURCE-MODEL-v2.md) 为准 —— 它是 CLI / 插件 / 后端三方的硬约束。
> 要「我要做 X 该声明什么」,看 [RESOURCE-CLASSES.md](RESOURCE-CLASSES.md);要规矩和线路格式,看 [PROTOCOL.md](PROTOCOL.md)。

---

## 1. 要解决的问题(一句话)

DSH 的控制面是完整的(谁在跑、任务状态、写入范围提示),**资源面完全缺失**(谁占着浏览器、谁开着端口、谁在用屏幕焦点)。后果:子 agent 一多就在独占资源上硬撞或静默串台,主控既看不见也无法调度。

本设计补的就是这一层:**把「独占资源」变成可申请、可持有、可释放、可超时、可被主控看见的一等对象。**

v2 在这句话后面加了一个更硬的目标:用户要的是「**任何形态的 agent 协作状态都不撞车**」。这句话一半能做到、一半做不到,§4 把它逐条摊开 —— 那是本文最重要的一节。

## 2. 三条设计原则(优先级从高到低,自 v1 未变)

1. **可见性优先于隔离。** 冲突只要看得见,主控就能重新调度;看不见的冲突会静默污染结果。所以第一交付物始终是「资源占用出现在每个 agent 的上下文里」,不是「更强的隔离」。
2. **失败即止,禁止静默重试。** 抢不到资源必须明确报错并把原因带回主控。静默重试会把控制冲突转化为时间浪费 —— 这正是用户感觉到的「资源浪费」的直接来源。
3. **租约永不永久有效。** 一切租约带 TTL,过期可被接管。agent 崩溃、进程被杀、插件卸载都必须能自动回收。**一个永远不释放的锁比没有锁更糟。**

v2 增加了一条实现纪律(不是新原则,是原则 2 的延伸):

4. **不确定就报错,不要降级。** broker 不可达、锁目录不可写、索引损坏 —— 都必须显式失败或显式声明降级为只读,**禁止静默继续**。所有「静默」在本设计里都等于「两个持有者」。

## 3. 三条不可退让的保证

写进实现和测试的硬约束:

- **G1 互斥**:任意时刻,同一 facet 上不存在两个互斥持有者。
- **G2 无死锁**:多资源获取不可能形成环形等待(靠 §7 的全局全序 + 逆序回滚)。
- **G3 可自愈**:持有者进程死亡后,其租约在下一次观测时被回收,不依赖 TTL 到点(§8)。

> 这三条能保证的是「**已声明资源上不撞车**」。
> 没声明的资源不可能被保证 —— 见下一节。

## 4. 保证边界(不许含糊)

用户的原话是「希望在任何形态的 agent 协作状态下都能保证不撞车」。诚实的回答是:**在声明过的资源上是真保证,在没声明的资源上是尽力而为 + 可观测,还有几件事根本做不到。**

下面三档必须原样区分,禁止在对外表述里合成一句「基本能保证」。

> 本节与 [PROTOCOL.md](PROTOCOL.md) §11 同源(一份给改代码的人,一份给 agent)。**改一处必须改另一处**,包括措辞强度 —— 两处出现「一处说保证、另一处说尽力」的分歧,比没有文档更糟。

### 4.1 真保证(有测试守护,可以打包票)

| # | 保证 | 靠什么 |
|---|---|---|
| 1 | **已声明资源上的互斥** | facet 冲突谓词 + `O_CREAT\|O_EXCL` 单次系统调用 |
| 2 | **多资源获取无死锁** | 全局稳定全序排序 + 逆序回滚(§7) |
| 3 | **持有者崩溃后自动回收** | 存活判定:同机 pid 不存在 / `procStart` 不符即回收(§8) |
| 4 | **不同写法的同一资源能被识别为冲突** | facet 展开:profile→目录、cdp→端口、祖先目录、端口区间(§6) |
| 5 | **跨进程、跨 session、跨 harness 实例** | 锁落在文件系统上,不在内存里 |

第 5 条是 v1 就有的:本机同时跑两个 harness 进程和无数 pwsh 子进程,内存锁对它们无效。第 4 条是 v2 新增,也是最容易被外行低估的一条 —— 「两个 agent 用了不同写法的同一个浏览器 profile」这类撞车,在 v1 里是查不出来的。

### 4.2 尽力而为(有用,但不叫保证)

| # | 场景 | 实际强度 |
|---|---|---|
| 6 | **没被声明的资源** | 没有任何机制能阻止一个 agent 直接 `fs.writeFileSync` 或直接 `spawn()`。观测式守卫(契约 §9)只能在**经由受保护工具**的调用上做参数扫描;**参数形态千变万化,不可能穷举** |
| 7 | **观测式守卫的覆盖面** | 只覆盖登记在 `protectedTools` 里、且参数能被规范化识别的工具。自带 shell 拼接、编码过的路径、非受保护工具调的写操作,全部漏过 |
| 8 | **真实键盘/鼠标交互** | `screen:focus` 串行化的是「谁有权送输入」,不保证「输入真的进了你以为的那个窗口」 |
| 9 | **跨机崩溃自愈** | G3 的「下一次观测立即回收」**只在本机成立**;跨 host 拿不到对方的进程表,只能等 TTL 过期(§8) |

第 9 条要说清楚,因为 G3 的措辞容易被读成全场景即时回收:**同 host 才是立即回收,跨 host 一律 TTL**。这是设计选择,不是缺陷 —— 想跨机拿进程表就得引分布式共识,那是 §13 明确拒绝的过度设计。

### 4.3 做不到(写进文档,不许假装)

1. **没声明的资源。** 见 4.2 第 6 条。这是本设计的**结构性边界**:任何基于「先声明再使用」的仲裁层,都无法约束绕过它的直接调用。要不撞车,前提是**协作方都走受保护通道**。
2. **符号链接 / 硬链接指向同一 inode。** 路径规范化**不解析符号链接** —— 解析会引入 TOCTOU 窗口(规范化时是 A,真正写入时链接已被换成 B)。后果:两个 agent 用两个不同的路径写法指向同一个文件时,**可能识别不出来**。缓解办法是约定同一写法,不是指望系统。
3. **跨机且 broker 不可达时。** 此时各机退化为本地锁,跨机互斥**失效**。契约要求这种情况**必须明确报错并降级为只读,不许静默继续** —— 「静默降级」比「直接失败」危险得多,因为所有人都以为自己受保护。
4. **进程内部自己开的线程/协程竞争。** 同一个进程里两个异步任务抢同一个资源,这不是资源租约的职责(租约的粒度是「持有者进程/会话」)。要管就在进程内自己加互斥。
5. **网络文件系统(NFS/SMB)上的 `O_EXCL` 语义不可靠。** 跨机必须走 broker,**不要共享锁目录**。共享目录做跨机仲裁是本设计最容易踩的「看起来能跑」的坑:单机测试全绿,真并发时两个节点同时创建成功。

### 4.4 对外怎么说这件事

| 别这么说 | 这么说 |
|---|---|
| 「保证不撞车」 | 「**声明过的**资源上不撞车,有测试守护;**没声明的**资源尽力而为、可观测,不叫保证」 |
| 「支持分布式」 | 「支持跨机,前提是所有节点指向同一个 broker;broker 不可达时明确失败,不静默降级」 |
| 「自动检测所有冲突」 | 「自动检测**能被规范化识别**的冲突;识别不了的靠约定和审计」 |

> 把这条边界写清楚,比承诺一个做不到的绝对保证更有价值。**一个被误信的假保证,会让所有人关掉自己的小心。**

## 5. 资源分类(A/B/C,自 v1 保留)与 v2 的 class 对应

三类冲突形态必须用三种模式表达,少一种就有表达不了的场景。

| 类型 | 例子 | 租约模式 | 撞车形态 | v2 里怎么写 |
|---|---|---|---|---|
| **A 独占单例** | 浏览器 user-data-dir、固定 CDP 端口、单例 app、**屏幕/输入焦点**、串口 | `exclusive`(slots=1) | 硬失败,或静默劫持(连上了但操作别人的东西) | `browser:profile:*` / `browser:cdp:<p>` / `port:<n>` / `screen:focus` / `window:hwnd:<n>` |
| **B 容量** | CPU/内存/GPU、Chromium 实例数、API RPM/TPM、并发连接 | `pool(slots: N)` | 不失败,退化成慢 → 超时 → OOM → 429 | `browser:instance`(pool)/ `api:<provider>:<metric>`(pool) |
| **C 共享可变状态** | 同一 cwd 文件、git index、数据库、共享写目标 | `exclusive`,键为路径祖先 | 静默污染:成功返回但结果错 | `path:<绝对路径>`(祖先 facet) |

> **B 类最容易被漏掉,而它恰好是本机的真实病灶。** N 个 agent 各调一次 `chromium.launch()`,谁也不「占锁」,但会把内存/CPU 打满、把 60s 工具超时撑爆。没有 pool 模式,这个病根本表达不出来。

v2 的变化在于 **C 类终于准确了**:v1 用「路径前缀字符串」表达共享写目标,`D:/out` 和 `D:/out2` 会被判成冲突(过度串行),`browser:profile:work` 和它对应的目录则被判成不冲突(漏判)。v2 的 facet + 分段祖先判定同时修好了这两头。

## 6. v2 新增(一):facet 冲突模型

**冲突不再是字符串相等,而是 facet 集合上的谓词。** 这是 v2 的地基。

一个 key 会展开成一组 facet:

```
expandFacets("browser:profile:work")
  → ["browser:profile:work", "path:<该 profile 的绝对路径>"]
```

于是这类最隐蔽的撞车被解决了 —— **两个 agent 用了不同写法的同一个资源**:

| 写法 A | 写法 B | 冲突? | 靠哪条 facet |
|---|---|---|---|
| `browser:profile:work` | `path:C:/Users/x/AppData/.../User Data` | ✅ | profile 路径 facet |
| `path:D:/out` | `path:D:/out/sub` | ✅ | 祖先-后代 |
| `path:D:/out` | `path:D:/out2` | ❌ | 祖先判定必须**按路径分隔符分段** |
| `port:9222` | `port:9220-9230` | ✅ | 区间重叠 |
| `browser:cdp:9222` | `port:9222` | ✅ | cdp 端口 facet |
| `window:hwnd:197772` | `browser:instance` | ⚠️ | 契约标了 ⚠️ 但蕴含表未给判定(见 §6 注) |

三条设计约束:

1. **规范形(canonical)是唯一判等依据。** 写入锁文件前规范化,读出来比较前也规范化。`sanitize` 只负责把规范形变成文件名安全的串,**不参与语义判等**(把 `sanitize` 当判等用,是典型的「两个不同资源撞成一个文件名」)。
2. **跨 class 的蕴含关系集中在一张表里**,不允许散落在调用点 —— 否则新增一类资源时必然漏一条。
3. **`screen:focus` 故意不与 `window:*` 冲突。** 焦点是输入流,窗口是目标对象;两个 agent 可以各持不同窗口但都需要焦点,所以由 `screen:focus` 串行化输入权即可。**让它们冲突会造成过度串行化**,而这正是 v1 「一个键干所有事」的反面。

> `path` 的祖先判定必须按路径分隔符分段。`D:/out` 与 `D:/out2` 不冲突 —— 这是 v1 最容易写错的地方,也是「过度串行化让人关掉仲裁」的起点。

> **§6 注:`window:hwnd:<n>` 与 `browser:instance` 的判定,契约还没给定论**(契约表里标了 ⚠️,但 §3.3 的蕴含表没有对应条目)。在此之前按最保守的方式用:要操作某个浏览器窗口时,把 `browser:instance`(或 `browser:profile:*`)和 `window:hwnd:<n>`、`screen:focus` 一起声明 —— 宁可多占一个 facet,不要赌「反正是不同 class」。

## 7. v2 新增(二):多资源原子获取

**一个操作通常同时占多个资源。** 传统写法 `acquire(A); acquire(B)` 有两个死法:拿到 A 之后 B 失败(占着一半不敢动),或者两个 agent 以相反顺序请求 A、B(环形等待)。

v2 的做法:

1. 每个请求展开成 facet,同一 facet 重复出现就合并(mode 取更强 `exclusive > shared`,slots 取 max)。
2. **按全局稳定全序(`orderKey`)升序排序** —— 这个序与「谁先申请」无关、与进程无关、与机器无关。全部参与者用同一个序,环形等待在数学上就不可能形成(G2)。
3. 逐个获取;某个失败就按 `strategy` 处理:`fail` 立即回滚,`queue` 轮询到超时再回滚。
4. **回滚必须逆序,且必须校验所有权**(`removeIfOwned`)。**按路径裸删会删掉别人的锁** —— 这是 v1 踩过的坑,后果是第三个 agent 进来,而两个人都以为自己独占。
5. 全部成功才写一条租约记录:一个 `leaseId` 覆盖一组 facet。

策略三档(自 v1 保留):

| 策略 | 语义 | 何时用 |
|---|---|---|
| `fail`(**默认**) | 立即返回明确错误,把持有者与剩余 TTL 一起带回 | 绝大多数场景。让主控决策,别让子 agent 硬闯 |
| `queue` | 等到超时,期间用于排队 | 调用方明确知道自己在等,且有超时上限 |
| `steal` | 强制接管(仅在持有者已过期/已死时合法) | 只给恢复流程用,不给普通调用 |

**冲突必须报「谁挡的」,而不是笼统失败。** 冲突载荷至少要含:冲突 facet + 持有者(agent/session/pid/host)+ reason + 剩余 TTL + 已回滚的键。少任何一项,主控就得自己去翻日志,可见性原则(原则 1)就破了。

## 8. v2 新增(三):存活判定优先于 TTL

v1 只认 TTL:进程被 kill -9 之后,锁要占到 TTL 结束。TTL 给 10 分钟的调试任务,崩溃残留就白占 10 分钟 —— 在 4 个 agent 并行时,这等于整批任务停转。

v2 的 owner 必填 `{ agent, session, pid, host, procStart }`,回收规则:

| 条件 | 处理 |
|---|---|
| 同 host,pid 不存在 | **立即回收**(G3) |
| 同 host,pid 存在但 `procStart` 不符 | **立即回收**(PID 被复用) |
| 跨 host | **只能靠 TTL**(拿不到对方进程表) |

`procStart`(进程启动时间,epoch ms,秒级精度足够)是 v2 新增的关键字段。没有它,PID 复用会导致「以为持有者还活着」,锁泄漏到 TTL 结束 —— 这类 bug 在短生命周期进程多的机器上很容易复现。

**回收不是无条件的。** v1 的两条安全规则必须保留,少一条就会一把锁两个持有者:

- **读不到内容的锁文件不等于过期。** 那多半是「刚创建、元数据还没写」的活着的持有者。只有文件同时**老于 2s** 才按崩溃残留处理。
- **接管后回读归档副本**:若它是有效未过期的租约,说明抢的是活锁,放回去并视为失败。

> 一句话:**判定「死了」比判定「过期了」更强,但证据不足时必须退回「视为活着」。** 宁可多占一个 TTL,也不要制造两个持有者。

## 9. v2 新增(四):后端抽象

存储不是实现细节,是**互操作契约**。v2 把它抽成接口:

- `tryCreate` —— `O_CREAT|O_EXCL` 语义,成败一次系统调用判定
- `read` / `remove`(必须校验所有权)/ `rename`(CAS,用于接管)/ `list` / `stat`

两种后端:

| 后端 | 实现 | 用在哪 |
|---|---|---|
| `local`(默认) | `fs`,零依赖 | 单机多进程(绝大多数场景) |
| `broker`(可选) | HTTP 服务实现同一语义,CAS 用 ETag / If-Match | 跨机;**必须接口一致,调用方不得区分后端** |

三条纪律:

1. **调用方不得探测后端类型。** 一旦代码里出现 `if (isBroker)`,跨机语义就会开始分叉。
2. **broker 不可达 = 明确报错 + 降级只读**,不许静默退化成本地锁(§4.3 第 3 条)。
3. **不要用共享网络目录代替 broker。** NFS/SMB 上的 `O_EXCL` 不可靠(§4.3 第 5 条),这条没有例外。

## 10. 数据模型

```jsonc
{
  "id": "lz_7f3a...",            // leaseId:一个 id 覆盖一组 facet
  "facets": ["browser:profile:work", "path:c:/users/me/appdata/.../user data"],
  "mode": "exclusive|shared|pool",
  "slots": 2,                    // 仅 pool 有意义
  "slot": 1,                     // 本租约占的那一个名额
  "owner": {
    "agent": "plugin-impl",      // agent 名/标识
    "session": "<sessionId>",
    "pid": 12345,
    "host": "MACHINE",
    "procStart": 1763200000000   // v2 新增:区分 PID 复用
  },
  "createdAt": 1763200000000,
  "expiresAt": 1763200060000,    // = createdAt + ttlMs
  "reason": "跑 Playwright 截图" // 给主控看的可读原因,必填
}
```

**`reason` 必填** —— 这是「主控知道子 agent 在干嘛」的最小信息量。一条 `browser:profile:work held by atk-3 (跑榜单截图,剩余 12s)` 胜过长篇日志。

v2 的模型变化只有两处:`facets` 是数组(v1 的 `key` 是单值,由 facets 派生),`owner` 多了 `procStart`。

## 11. 存储与跨进程

**必须落在文件系统上,不能只在内存里。**

```
<lockRoot>/<sanitized-facet>.lock            每个 facet 一个文件(v1 兼容,v2 的判等依据)
<lockRoot>/<sanitized-facet>.slot-<N>.lock   pool 的第 N 个名额
<lockRoot>/_leases/<leaseId>.json            聚合索引:本租约占了哪些 facet
<lockRoot>/<name>.lock.stale.<epoch>.<pid>   接管后的归档
```

两条关键设计:

1. **facet 文件是唯一的判等依据,索引只是索引。** 索引丢了、坏了、被删了,互斥仍然正确 —— 这一点很重要:**索引损坏不能导致死锁**。反过来,索引齐全但 facet 文件不对,照样能挡住人。
2. **释放按 `leaseId` 进行**:读索引 → 逐个 `removeIfOwned` → 删索引。释放**必须校验所有权**,否则「过期 → 被接管 → 旧持有者释放」会删掉新持有者的有效锁。

原子性、接管 CAS、锁格式请直接看 [PROTOCOL.md](PROTOCOL.md) §7 —— 那里是线路契约,这里是设计理由。

> **锁格式是两层共用的契约。** CLI 与插件必须读写同一套锁文件,否则「用 CLI 的 agent」和「用插件的 agent」互相看不见对方,仲裁等于没有。改格式等于破坏兼容。

|---|---|

## 13. 非目标

v1 列了五条。**v2 把其中两条划掉了** —— 因为「任何形态都不撞车」这个目标必须包含它们;另外三条仍然成立。

| v1 非目标 | v2 状态 |
|---|---|
| ~~不做跨机器/分布式租约(单机 + 多进程足够)~~ | ❌ **已划掉,已实现**。理由:「任何形态」包含多机。改了什么:新增**后端抽象**(`local` / `broker`,§9)+ 跨机存活只能靠 TTL(§4.2 第 9 条)+ broker 不可达必须报错降级。**注意这不是 Raft**,broker 用简单 CAS 就够 |
| ~~不做自动资源推断(资源由调用方显式声明;推断是 v2)~~ | ❌ **已划掉,已实现**。理由:没声明的资源也要能「撞见」。改了什么:新增 **facet 展开**(不同写法识别为同一资源,§6)+ **观测式冲突检测**(扫受保护工具的参数,与已持有 facet 求交)。**这一条是尽力而为,不是保证**(§4.2 第 6/7 条) |
| 不做优先级抢占(先有排队和失败,再谈优先级) | ✅ **仍不做**。抢占会把冲突变成数据损坏 —— 高优先级 agent 打断正在写盘的持有者,产出一个两边都不完整的文件 |
| 不做 Web UI 面板(MVP 走 prompt 注入 + `resource_status`) | ✅ **仍不做**(v2 未排期) |
| 不改 DSH 源码,只做外挂插件 | ✅ **仍是原则**(v2 未变) |

v2 新增的明示不做:

- **不做分布式共识 / Raft。** broker 用简单 CAS 足够,引共识是过度设计。
- **不做符号链接解析。** TOCTOU 风险大于收益(§4.3 第 2 条)。
- **不推断「这个操作需要哪些资源」。** 推断错误比漏判更危险:猜错会让人以为自己受保护,而漏判至少还看得见。

> v1 的 `cli/README.md` 在「已知局限」里还记了两条,现在都随 v2 不成立,读那份文档时要带着这个前提:
> 「单机 + 多进程,不做跨机器租约」—— 由 §9 后端抽象解决;
> 「不检测持锁进程是否还活着,只认 TTL」—— 由 §8 存活判定解决。
> 同节的「不做优先级抢占」与「`shared` 与 `exclusive` 行为一致」**仍然成立**。

## 14. 失败模式与对策

| 失败 | 对策 |
|---|---|
| agent 崩了没释放 | 存活判定立即回收(同机);跨机靠 TTL 过期 + 接管日志 |
| PID 被复用 | `owner.procStart` 不符 → 立即回收 |
| 插件卸载 / agent 销毁 | effect disposer 释放全部租约 |
| 两个 harness 进程抢同一资源 | 文件系统锁,天然跨进程 |
| 锁目录被删 / 权限不足 | 启动自检,失败则**明确报错并禁用插件**,不静默降级 |
| broker 不可达 | **明确报错并降级为只读**,禁止静默退化为本地锁 |
| 索引 `_leases/` 损坏或丢失 | 互斥不受影响(facet 文件为准);索引可按 facet 文件重建 |
| 多键获取中途失败 | 逆序回滚 + `removeIfOwned`,不留残留 |
| 调用方忘记释放 | `run` 包装 + guard 拒绝 + TTL 三重兜底 |
| 资源键拼写不一致 | 规范形判等 + facet 展开;**但没声明的键不可救**(§4.2) |
| 长任务跑超 TTL 被接管 | 按最坏情况给 TTL;常驻进程用 `run` 绑生命周期;接管后只记日志**不删对方的锁** |

## 15. 常见误用

| 误用 | 为什么错 | 正确做法 |
|---|---|---|
| **用目录当锁** | 目录锁的成败取决于「创建时是否抛异常」:普通 `New-Item -ItemType Directory` 对已存在目录会报错,但 `-Force`、`[System.IO.Directory]::CreateDirectory`、`mkdir -p` **不抛** —— 每个 racer 都「成功」,互斥**静默失效**。第一版就是在这个歧义上栽的(3 个进程抢 2 个名额,3 个全进) | 锁 = **一个文件**,`O_CREAT\|O_EXCL`(`fs.openSync(path,'wx')` / `FileMode::CreateNew`),单次系统调用判定 |
| **按路径裸删锁文件** | 你可能删掉一个活着的有效租约(文件存在 = 有人持有),或删掉「已被别人接管的新锁」。前者制造两个持有者,后者让第三个 agent 进来而新持有者仍以为独占 | 一律 `removeIfOwned`(校验 leaseId/owner)或 `release --id`;崩溃残留靠 `EXPIRED(takeable)` 识别后走接管流程 |
| **以为 `shared` 能防写冲突** | `shared` 只表达「读意图」;谓词里 `shared`+`shared` 是**放行**。两个要写的 agent 都用 `shared` = 双人裸奔。而且磁盘上 `shared` 仍占一个单锁文件,你还会意外串行化 | 会写就用 `exclusive`;要并发读用 `pool` 或不声明 |
| **把 `screen:focus` 与 `window:hwnd` 混为一谈** | 两者故意不冲突:焦点是输入流,窗口是目标对象。只拿 `window` 的人可能把键鼠打进别人窗口;只拿焦点的人可能操作错窗口 | 要往某窗口送输入就**两个都拿**,一次 acquire |
| **路径祖先用字符串前缀比较** | `D:/out` 会把 `D:/out2` 判成自己的后代 → 过度串行;反过来漏判更糟 | 按路径分隔符**分段**比较 |
| **用 `sanitize` 当判等依据** | `sanitize` 是为文件名安全服务的(映射非法字符、限长、加短哈希),`browser:chromium` 与 `browser_chromium` 会落到同一文件名,但它们是不同资源 | 语义判等永远用 canonical key / facet |
| **把 G3 当成全场景即时回收** | 「下一次观测立即回收」只对**同 host** 成立;跨机拿不到进程表,只能等 TTL | 跨机场景按 TTL 设计任务时长,别假设崩溃会立刻让位 |
| **认为锁格式可以随手改** | 锁格式是 CLI / 插件 / broker 三方共用契约,改格式等于让两套仲裁互相失明 | 改格式 = 破坏兼容,必须三方同时升级 |

## 16. 一句话总结

> **v1 解决的是「谁占着什么看得见」。v2 解决的是「不同写法的同一资源、一次要占多个资源、进程已经死了」这三件事。**
> 而「任何形态都不撞车」这句目标,落到文档上必须写成:**声明过的真保证,没声明的尽力而为,做不到的直说。**
